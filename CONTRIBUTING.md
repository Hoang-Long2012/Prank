# Contributing to Prank

Thank you for your interest in contributing to **Prank**.

Prank is a Python package dedicated to one important mission:

> Turning every uncaught exception into emotional damage.

Contributions are welcome, provided they do not accidentally turn Prank into a useful piece of software.

## Before You Contribute

Please understand what you are getting yourself into.

Prank is intentionally useless.

It is not:

* A debugging framework.
* An error-recovery system.
* A logging framework.
* A productivity tool.
* A solution to your bugs.
* A replacement for therapy.

If you are looking for any of the above, you may have opened the wrong repository.

## What Makes a Good Contribution?

A good contribution should satisfy at least one of the following:

* Makes exceptions funnier.
* Makes emotional damage more effective.
* Improves code quality without removing the chaos.
* Adds a genuinely useful internal improvement.
* Makes the package easier to install or use.
* Fixes an actual bug.
* Makes the maintainers wonder why someone spent time implementing it.

Bonus points if it accomplishes all of the above.

## What Makes a Bad Contribution?

The following contributions may be rejected:

* Removing the sarcasm.
* Making Prank completely serious.
* Turning Prank into a debugging tool.
* Adding unnecessary dependencies.
* Adding a 50 MB dependency to generate one joke.
* Introducing a configuration file containing 300 options.
* Replacing simple code with unnecessary enterprise architecture.
* Removing intentionally funny behavior.
* Fixing something that was deliberately funny.
* Making the package useful enough to lose its identity.

If your pull request makes Prank more productive than entertaining, something has gone terribly wrong.

## Development Setup

Clone the repository:

```
git clone https://github.com/Hoang-Long2012/Prank.git
cd Prank
```

Create a virtual environment if desired:

```
python -m venv .venv
```

Activate it according to your operating system.

Then install the project in editable mode:

```
pip install -e .
```

Congratulations.

You are now legally allowed to break things locally.

## Code Style

Please keep the code:

* Readable.
* Maintainable.
* Simple.
* Pythonic.
* Consistent with the existing project.

Do not over-engineer a joke.

If a three-line function requires a twelve-class architecture, please step away from the keyboard and reconsider your life choices.

## Testing

Contributions should be tested before submitting a pull request.

At minimum, verify that:

1. Prank can be installed.
2. `prank.install()` works.
3. Uncaught exceptions still produce prank messages.
4. `prank.uninstall()` works.
5. `prank.is_installed()` reports the correct state.
6. Normal Python exception behavior is not unnecessarily destroyed.

Remember:

> The goal is to prank the exception, not the entire Python interpreter.

## Pull Requests

Before opening a pull request, please make sure that:

* Your code works.
* Your changes are focused.
* Existing functionality is not unnecessarily broken.
* You have tested your changes.
* Your commit messages are understandable And if possible, make them funny.
* You have not accidentally reinvented Python.

Your pull request description should explain:

* What changed.
* Why it changed.
* How it was tested.
* Whether it causes additional emotional damage.

### Pull Request Review

Pull requests are evaluated using the following highly sophisticated review methodology:

**Step 1:** Does it work?

**Step 2:** Is it funny?

**Step 3:** Does it preserve the spirit of Prank?

**Step 4:** Did the contributor unnecessarily over-engineer something?

**Step 5:** Why did you do this?

If the answer to Step 5 is "I don't know", the pull request may already be excellent.

## Bug Reports

Found a bug?

Excellent.

Please open an issue and include:

* Python version.
* Operating system.
* Prank version.
* Steps to reproduce the problem.
* Expected behavior.
* Actual behavior.
* Relevant traceback or error message.

Please do not report the following as bugs:

> "My program crashed."

That's literally the point.

However, if **Prank itself** crashes while trying to prank another exception, congratulations.

You have discovered a bug worthy of an issue.

## Feature Requests

Feature requests are welcome.

However, please remember that Prank has a very strict product philosophy:

> **More emotional damage. Less productivity.**

Examples of potentially acceptable features:

* More sarcastic messages.
* Better exception detection.
* More ridiculous rare messages.
* Additional harmless Easter eggs.
* Improvements to installation and uninstallation.
* Better compatibility with supported Python versions.

Examples of questionable features:

* AI-powered debugging.
* Automatic bug fixing.
* Full-stack observability.
* Distributed tracing.
* Kubernetes integration.
* Blockchain-based exception handling.

Please do not submit a pull request adding Kubernetes to Prank.

We are begging you.

## Dependencies

Prank currently aims to remain lightweight.

Before adding a dependency, ask yourself:

> "Can this be done with the Python standard library?"

If yes, seriously consider using the standard library.

If the proposed dependency exists solely to print one sarcastic sentence, the answer is probably no.

## Compatibility

Changes should preserve compatibility with supported Python versions whenever reasonably possible.

Do not intentionally break users just because it would be funny.

That is the job of their own code.

## Documentation

Documentation improvements are welcome.

Documentation should be:

* Accurate.
* Clear.
* Concise.
* Slightly suspicious.

Humor is encouraged, but documentation must still explain how the software actually works.

A user should never need to read the source code just to figure out how to uninstall Prank.

## Commit Messages

Please use clear commit messages.

Good:

```
Add rare exception messages
Fix uninstall state detection
Improve exception hook handling
Update documentation
```

Acceptable:

```
Make exceptions sadder
Increase emotional damage
The traceback is now funnier
```

Discouraged:

```
lol
stuff
asdf
why
it works on my machine
```

## Security

If you discover a genuine security vulnerability, please do not publicly disclose sensitive details before there is an opportunity to address it.
